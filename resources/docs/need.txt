QUESTIONS — answered, kept here for reference
=====================================================================

Q1. Are we using WebFlux?
A1. Yes, but ONLY in `api-gateway`. Spring Cloud Gateway is built on WebFlux/Netty.
    The four business services are servlet MVC (Spring MVC).
    Why: reactive code is harder to read and to debug, and our business logic is short
    bursts of database work where reactive buys nothing. The gateway is pure IO
    proxying, where it genuinely shines — so you see both stacks in one project.
    You will also see the consequence: a servlet `Filter` does not exist in a reactive
    stack, so the gateway needs its own WebFilter for correlation ids (Day 7).

Q2. Can we use R2DBC in one service and JPA in another, to compare?
A2. Not as the architecture — that would double the persistence surface, split the
    learning, and pay a real cost for a workload we do not have. But the COMPARISON
    is genuinely valuable for interviews, so it is offered as a lab instead:
    build the SAME endpoint twice (JPA + blocking, then R2DBC + WebFlux), measure
    throughput under load, and write up the tradeoff. Same answer, no contamination.
    Candidate for Phase EXTRA Day 25.

Q3. I want to understand @Transactional, concurrent SQL writes, and failure handling.
A3. Covered, in three explicit places:
    - Day 2  -> transaction boundaries, propagation, rollback rules, isolation levels
    - Day 8  -> the 2-subscription quota race: solve it with a DB constraint,
                SELECT ... FOR UPDATE, and a Redis counter. Deliberately write a
                FAILING concurrency test first, so you SEE the lost update, then fix it.
    - Day 11 -> why "write to DB then publish to Kafka" is not atomic (transactional outbox)
    - Day 14 -> idempotency and compensation when a step fails after money moved

Q4. Are we implementing the SAGA pattern?
A4. Yes — Day 14, choreography style, for the payment -> tier-upgrade flow, including
    compensating actions and a reconciliation job for "paid but upgrade failed".
    Orchestration (a central state machine) is discussed and rejected on purpose:
    one flow does not justify an orchestrator, and choreography is the better default.
